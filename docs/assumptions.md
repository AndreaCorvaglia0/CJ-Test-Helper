# Salesforce assumptions to verify

11 October 2026. Review of the journey model and the data rules against Journey Builder, Contact Builder and Automation Studio, on the pilot export `fixtures/CJ template complesso-v1.json`.

Each row is a point where the generator's output depends on platform behaviour that `docs/spec.md` does not settle. None of them is to be decided in code: each one stays visible (a setting, a warning or a report line) until a small real run confirms it. Rows 1 to 6 are the spec's own list; rows 7 to 35 come from this review.

How the documentation was checked: Salesforce Help, the developer guide, Trailhead and Salesforce knowledge articles were searched on 11 October 2026. The pages themselves could not be opened from this environment (the network proxy refuses help.salesforce.com), so the quotes below are the extracts returned by the search engine; re-read a quote on its page before citing it to the client. "Official" means a Salesforce page. "Nothing official found" means no Salesforce page turned up. Pilot facts were checked on the export; generator facts on two runs of the current command line (`--time "2026-10-12 10:00" --inbox tester@example.com`, with and without `--case-insensitive`).

## Check these first

1. Rows 23 to 27, entry: importing the entry CSV admits nobody. The automation has to run, and a full run also executes the entry query and the Verification step. Choose the entry method before the first real run.
2. Row 32, retention: all seven data extensions carry a retention policy in the export. If it is active in the test business unit, data disappears during the run.
3. Row 2, letter case: it moves 46 branches between covered and not covered, and changes the expected path of 59 of the 146 contacts in the default output (9 in three scenarios, plus the 50 of the statistical case).
4. Row 7, an empty `EmailOptOut` against `Is false`.
5. Row 15, whether opens of the pilot email are recorded at all.

## Verification run

One run in the test business unit settles most rows. It takes about a day because of the waits.

Before importing: deploy the package; read the retention policy of the seven data extensions (row 32); pause the schedule of `A_SkyDE_NCRM_AdHoc_CJ_entry`; activate the journey; open the automation and find the journey-entry activity that activation added (row 23).

## Suspicious patterns in the pilot worth flagging in the report

- All six engagement splits reference EMAILV2-1, including the ones after the channel-2 and channel-3 emails (EMAILV2-2, EMAILV2-19). Their Yes branches cannot be taken where EMAILV2-1 was not sent.
- CHANNEL2 and CHANNEL3 are compared with `'EMAIL'` in "channel 2 email?" (MULTICRITERIADECISIONV2-42) and "channel 3 email?" (-116), and CHANNEL4 with `'EMAIL'` in three "Channel4" splits (-117, -144, -153), while every other channel split, including "Channel 4" (-33), uses `'Email'`.
- 23 update steps (11 DM, 11 OB, 1 CG) write the constants `DemoSKY` and `ActionId` into the primary-key fields CampaignName and ActionId of `DE_SkyDE_AdHoc_Log_partial`. Each contact gets one Log row that every later step overwrites, and the Log never records the real campaign or action. The value `ActionId` looks like a field name typed as a constant.
- The 11 SMS steps are placeholders that write `Control Group = 1` into the entry table `DE_NCM_AdHoc_Entry` (on every row of the contact, since the key is composite). SMS contacts end up flagged as control group in the entry table, while the real control-group branch (UPDATECONTACTDATAV2-1) writes `'true'` into the Log's Text field "Control Group": one concept, two tables, two types.
- The 11 "Phone consent" splits on the SMS paths test only IsMailOffers, while the 11 on the OB paths test IsMailOffers, IsDunning and PhoneConsent: SMS does not check PhoneConsent.
- EmailOptOut (nullable, no default) is tested only with `Is false`, while IsDunning is tested with `Is false OR IsNull`. The null handling is inconsistent; if null does not match false, contacts with an empty EmailOptOut never get an email.
- The entry query selects 26 Master columns that the entry table does not have, and the email greets with `AttributeValue("FirstName")`, which is not in the entry data: the greeting is likely empty. Content is out of scope, but the select list shows the author expected those fields in the entry table.
- Two event definitions (`CJ_SkYDE_NCRM_Demo` and `CJ_SkYDE_NCRM_Demo_final`) are bound to the same automation and the same entry table, and the journey's mobile default reads the old one (already reported by the loader).
- Master to Entry is declared One-to-One although the entry table's key (ContactId, ActionId, CampaignName) allows several rows per contact; Entry to Config is declared One-to-One although every contact of a campaign points to the same Config row.
- The Verification step stops the automation whenever the number of active campaigns is not exactly 1, so it also stops when none is active; its notification text mentions only multiple active campaigns.
- `Q_SKYDE_NCRM_AD_HOC_CONFIGURATION_UPDATE` deactivates only campaigns whose RUN_TIME is empty and that have entry rows. A campaign with RUN_TIME filled stays active, and every scheduled run (every 2 hours) enters its contacts again with a new ActionId. The deduplication against the entry table in the entry query is commented out, so this flag is the only protection against re-entry.
- `Q_Check_Active_campaigns` copies CampaignName (Text 250) into `DE_Check_Active_Campaigns.CampaignName` (Text 50): an active campaign name longer than 50 characters would break that step.
- `Q_SkyDE_AdHoc_Backup` copies Entry.Emailaddress (nullable) into DE_NCRM_AdHoc_Entry_Backup.Emailaddress (not nullable): an entry row without an email address would break the backup step.
- All seven data extensions carry a retention policy in the export (period 1, unit code 3, delete at end of period, not row based).
- The email is an HTML-paste email with no link and no open-tracking element; the package asks for an Operational (transactional) send classification at deployment, and Sales Cloud tracking is on. Clicks are impossible and opens may not be recorded (row 15).
- The wait-by-attribute dates are campaign-level (Config.WAIT1 to WAIT3): every contact of a scenario waits until the same moment, so one case that needs a 24-hour engagement window holds every case of that scenario for 24 hours.

## Things the model gets wrong or that are missing

1. Entry method. The spec has the tester import the entry CSV directly and never combine it with an automation run, but with this entry source an import admits nobody (row 23). Two methods work, each with its own data and testbook steps, so the method should be a setting:
   - Direct import: import the four CSVs, then Run Once with only the journey-entry activity (row 24, to verify). Every scenario's contacts enter at once; the activation field has no effect; the Verification step and the queries must not run.
   - Full run (the earlier tool's method): import Master, Target and Config but not the entry CSV, and run the whole automation once per scenario with exactly one Config row ACTIVE (row 27). Here "edit only the activation field" works, and "one active scenario" must stay on for the pilot.
2. Config.RUN_TIME must be empty. Today every Config row gets the generation time. With the full-run method, the post-run query (`WHERE RUN_TIME IS NULL`) then never deactivates the scenario: the next run either stops at the Verification step (two ACTIVE rows) or, on the 2-hour schedule, enters the same contacts again. A field that any query of the entry automation tests with `IS NULL` should be left empty. Related: tables.py follows that query back as if it fed Config, but it runs in step 4, after the entry query (step 3), and reads the entry table. It is post-processing; its filters are conditions to respect, not values to copy.
3. Generation time has no time zone. `pipeline.py` uses `datetime.now()`, so the same settings give different real waits on a PC in Italy and on a UTC server (row 6). The settings should name the zone the dates are written in. The default "the wait ends at once" would be safer as a date well in the past (for example generation time minus 24 hours), which ends the wait whatever zone Salesforce applies (row 3 is documented). ActionId should use UTC like `GETUTCDATE()` (cosmetic).
4. Letter case decides 59 contacts today: the 9 of S12, S13 and S16, and the 50 of the statistical S23 on its 90% side. S12, S16 and S23 store `EMAIL` where a split tests `Email`; S13 stores `Email` where "channel 2 email?" tests `EMAIL`. Until row 2 is verified, the report should list the cases whose expected path differs between the two settings, and the cover could prefer values whose routing is the same under both readings.
5. Null values. Keep choosing non-null values for contact classes when a non-null value gives the same truth vector (the default output already does), so no expected path hinges on row 7; use null only where a branch needs `IsNull`.
6. Contact Data and Journey Data. `Condition` has no data-source flag. Every pilot condition is Contact Data, but the spec's rule "a later split that reads the same field sees the updated value" holds only for Contact Data; a Journey Data condition (`Event.<key>.<field>`) is fixed at entry (row 11), and its key would not map to an attribute set.
7. Update Contact on composite keys. `Write` records values per step; on the pilot's Log (constant key) all of a contact's writes land on one row, last write wins per field, and the SMS writes change every Entry row of the contact (row 18). The testbook's "values written by the journey" should be stated per row, not per step.
8. Retention is not in the model. `Table` has no retention fields; carrying `dataRetentionProperties` would let the report warn about any selected table with a policy (row 32).
9. Wording. The report states that the entry query's extra columns "are ignored"; that is row 28, unverified, and should read as an assumption.
10. Contacts. Every generation creates new contact keys (146 in the default pilot output, 224 with case ignored), and each one becomes a contact of the business unit when it enters the journey. Agree with the client how test contacts are deleted. (Not checked against documentation.)
